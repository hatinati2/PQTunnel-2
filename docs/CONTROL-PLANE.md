# مرکز کنترل مرکزی PQTunnel (آزمایشی)

**وضعیت: پیاده‌سازی اولیه؛ هنوز برای استفادهٔ عملیاتی یا نصب روی VPS حساس تأیید نشده است.**

این سند معماری و نصب اولیهٔ Control Plane را توضیح می‌دهد. هدف این است که اپراتور از یک مرورگر موبایل بتواند Gateway و یک Dialer را از یک داشبورد مدیریت کند؛ برای کارهای روزمره SSH لازم نباشد.

## معماری

- **Gateway** میزبان پنل مرکزی و Broker است. پنل فارسی و واکنش‌گرا با یک توکن ورود مستقل محافظت می‌شود.
- **Dialer** یک سرویس کوچک به نام `pqtunnel-agent` اجرا می‌کند. Agent اتصال خروجی را به مسیر محرمانهٔ Gateway باز می‌کند؛ پنل برای مدیریت Dialer به SSH یا بازکردن پورت ورودی روی Dialer نیاز ندارد.
- ارتباط Agent با Broker از HTTPS عبور می‌کند، اما پیام‌های وضعیت، فرمان، نتیجه و پروفایل با AES-256-GCM رمز می‌شوند. ثبت‌نام با کلید موقت X25519 انجام می‌شود و کلید Agent در فایل root-only هر سمت نگهداری می‌شود.
- دعوت Dialer یک‌بارمصرف است، ۱۵ دقیقه اعتبار دارد و بعد از ثبت موفق مصرف می‌شود. در حالت فعلی فقط یک Dialer برای هر Gateway پذیرفته می‌شود.
- پنل از همان پورت HTTPS و همان مسیر تصادفی ۲۵۶ بیتی استفاده می‌کند که نصاب مدیریت تولید می‌کند. مسیر `/agent/...` نیز زیر همین مسیر محرمانه قرار می‌گیرد.

## قابلیت‌های داشبورد اولیه

پس از ثبت Agent، یک ورود برای دیدن این موارد استفاده می‌شود:

- وضعیت سرویس، وضعیت Agent و زمان آخرین ارتباط هر سمت
- شروع، توقف و راه‌اندازی مجدد سرویس Gateway و Dialer
- مشاهدهٔ آخرین لاگ سرویس هر سمت
- ویرایش تنظیمات پشتیبانی‌شدهٔ تونل: Listen address، Server address/name، CIDRهای محلی/همتا و allowlist پورت‌های مقصد
- صدور دعوت یک‌بارمصرف Dialer و تولید دستور نصب آن
- جفت‌سازی اولیهٔ دو سرور: تولید پروفایل عمومی Gateway، ارسال رمز‌شده به Dialer، ساخت کلید/گواهی Dialer روی خود Dialer و بازگرداندن پروفایل عمومی Dialer برای ثبت در Gateway

کلیدهای خصوصی از هیچ‌کدام از سرورها خارج نمی‌شوند. بعد از جفت‌سازی، سرویس‌های تونل عمداً خاموش می‌مانند؛ اپراتور باید شروع هر دو سمت را جداگانه از پنل تأیید کند.

## نصب یک‌خطی

ابتدا از صفحهٔ GitHub نسخه/commit بازبینی‌شده را انتخاب کن. برای نصب باید از SHA چهل‌کاراکتری همان commit استفاده شود؛ نام شاخه‌هایی مثل `main` یا `feat/...` عمداً پذیرفته نمی‌شوند. این placeholder را با SHA واقعی جایگزین کن:

### روی Gateway

```sh
curl -fsSL https://raw.githubusercontent.com/hatinati2/PQTunnel-2/COMMIT_SHA/scripts/pqtunnel-control-install.sh | sudo bash -s -- --ref COMMIT_SHA --role gateway --panel-domain control.example.com --panel-port 6100
```

- `control.example.com` را با دامنه‌ای جایگزین کن که رکورد DNS آن به IP عمومی Gateway اشاره می‌کند.
- نصاب با Certbot یک گواهی معتبر Let's Encrypt می‌گیرد؛ برای صدور و تمدید خودکار، TCP/80 باید از اینترنت به Gateway برسد.
- `--panel-port` پورت HTTPS پنل است؛ پیش‌فرض `6100` و باید در فایروال سیستم و ارائه‌دهنده باز باشد.
- نصاب وابستگی‌های لازم را در Ubuntu/Debian نصب می‌کند. اگر Go 1.27 یا جدیدتر موجود نباشد، نسخهٔ سازگار را از منبع رسمی دانلود و SHA256 آن را بررسی می‌کند؛ سپس بستهٔ Linux را از همان commit می‌سازد و نصب می‌کند.
- پس از نصب، URL خصوصی پنل و توکن ورود در خروجی ترمینال نشان داده می‌شود. آن‌ها را در محل امن ذخیره کن.

### روی Dialer

از پنل Gateway، بخش «افزودن Dialer» را باز کن و دعوت یک‌بارمصرف بساز. پنل یک دستور نصب کامل و مختص همان Gateway تولید می‌کند. آن دستور را فقط روی سرور Dialer اجرا کن. پس از نصب، Agent به‌صورت سرویس systemd فعال می‌شود و وضعیتش در داشبورد Gateway ظاهر خواهد شد.

مرحلهٔ enrollment و تمام پیام‌های Agent فقط از HTTPS با اعتبارسنجی استاندارد گواهی عبور می‌کنند. Agent آدرس HTTP یا مسیر فاقد توکن ۲۵۶ بیتی را رد می‌کند.

## چه چیزی در این نسخه مدیریت می‌شود و چه چیزی نه؟

داشبورد نسخهٔ اولیه، lifecycle سرویس‌ها، تنظیمات تونل، پروفایل‌های PKI و لاگ‌ها را از راه Agent مدیریت می‌کند. اما این به معنی مدیریت کامل کل شبکهٔ سیستم‌عامل نیست.

به‌طور مشخص، helper فعلی TUN رابط `pqtun0` و IPهای آزمایشی آن را می‌سازد، اما به‌صورت خودکار default route، policy routing، NAT، forwarding یا قوانین firewall را پیکربندی نمی‌کند. کنترل کامل egress، port-forwarding و kill-switch باید در مرحلهٔ بعد با مدل snapshot/rollback و تست روی namespaceهای ایزوله طراحی و به پنل افزوده شود. بنابراین موفقیت جفت‌سازی در این نسخه به‌تنهایی به معنی آماده بودن مسیر ترافیک دلخواه یا آماده‌بودن برای تولید نیست.

اگر Agent روی Dialer آفلاین شود، کنترل از Gateway ممکن نیست تا وقتی ارتباط خروجی Agent دوباره برقرار شود. پنل مرکزی برای بازیابی خود Gateway باید از همان پورت و مسیر Gateway قابل دسترس باشد؛ این سیستم هنوز افزونگی کنترل‌پلین یا failover ندارد.

## امنیت کانال مدیریت

پنل عمومی و کانال Agent از HTTPS با گواهی معتبر Let's Encrypt استفاده می‌کنند. کوکی نشست با ویژگی `Secure`، `HttpOnly` و `SameSite=Strict` صادر می‌شود. پنل محلی loopback برای دسترسی از طریق SSH port-forwarding همچنان در دسترس است؛ پورت عمومی plaintext HTTP توسط Manager رد می‌شود.

برای ACME HTTP-01، دامنه باید به IP Gateway resolve شود و TCP/80 باید برای صدور و تمدید خودکار گواهی قابل دسترس باشد. خود پنل روی TCP پورت انتخابی (پیش‌فرض 6100) با TLS 1.3 ارائه می‌شود. Agent نیز فقط URL با scheme برابر HTTPS و مسیر محرمانهٔ ۲۵۶ بیتی می‌پذیرد؛ اعتبارسنجی گواهی سیستم عامل غیرفعال نمی‌شود.

رمزگذاری AES-GCM پیام‌های Agent دفاع تکمیلی در سطح برنامه است و جای TLS را نمی‌گیرد. هیچ مسیر HTTP عمومی برای مدیریت یا Enrollment پشتیبانی نمی‌شود.

## وضعیت اعتبارسنجی

- تست‌های واحد Agent/Broker و UI، replay protection، enrollment، command delivery و build/race/static analysis باید در GitHub Actions اجرا شوند.
- تست‌های CI در namespaceهای موقت‌اند؛ آن‌ها دو VPS واقعی، فایروال ارائه‌دهنده، کیفیت مسیر ایران، یا بازیابی از قطع کامل دسترسی را تأیید نمی‌کنند.
- هنوز تست عملی دو میزبان، ممیزی امنیتی مستقل و release امضاشده انجام نشده است.
- این راهنما را روی VPS عملیاتی اجرا نکن تا PR بررسی و ادغام، Release بازبینی‌شده و runbook بازیابی واقعی تکمیل شده باشد.
