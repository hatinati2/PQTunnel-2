# مرکز کنترل مرکزی PQTunnel (آزمایشی)

**وضعیت: پیاده‌سازی اولیه؛ فقط برای آزمایش روی دو VPS جداگانه. برای استفادهٔ عملیاتی تأیید نشده است.**

این راهنما نصب نسخهٔ آزمایشی Control Plane را توضیح می‌دهد. هدف این است که از مرورگر موبایل یا کامپیوتر، Gateway و یک Dialer را از یک داشبورد مدیریت کنیم.

## معماری

- **Gateway** میزبان پنل مرکزی و Broker است. پنل فارسی و واکنش‌گراست و با توکن ورود مستقل و مسیر تصادفی ۲۵۶ بیتی محافظت می‌شود.
- **Dialer** سرویس `pqtunnel-agent` را اجرا می‌کند و اتصال خروجی را به Gateway برقرار می‌کند؛ برای مدیریت Dialer نیازی به SSH یا پورت ورودی عمومی روی Dialer نیست.
- پنل و ارتباط Agent در این build آزمایشی از **HTTP ساده** استفاده می‌کنند.
- پیام‌های عملیاتی Agent پس از ثبت‌نام با AES-256-GCM رمز می‌شوند. ثبت اولیه از X25519 استفاده می‌کند؛ با این حال توکن دعوت اولیه و نشست مرورگر روی HTTP در برابر شنود شبکه محافظت نمی‌شوند.
- دعوت Dialer یک‌بارمصرف است، ۱۵ دقیقه اعتبار دارد و بعد از ثبت موفق مصرف می‌شود. در حالت فعلی فقط یک Dialer برای هر Gateway پشتیبانی می‌شود.
- شمارندهٔ ضد Replay روی Gateway و وضعیت فرمان/نتیجهٔ Agent روی Dialer بعد از Restart ذخیره می‌شوند.
- اگر Agent هنگام اجرای فرمان از کار بیفتد، پس از راه‌اندازی نتیجهٔ نامشخص اعلام می‌شود و فرمان خودکار تکرار نمی‌شود.

## قابلیت‌های داشبورد

- وضعیت سرویس، وضعیت Agent و آخرین زمان ارتباط
- شروع، توقف و راه‌اندازی مجدد سرویس‌های Gateway و Dialer
- مشاهدهٔ لاگ‌های سرویس
- ویرایش تنظیمات پشتیبانی‌شدهٔ تونل
- صدور دعوت یک‌بارمصرف Dialer و تولید دستور نصب
- جفت‌سازی اولیهٔ دو سرور و انتقال پروفایل‌های عمومی از کانال Agent

کلیدهای خصوصی روی همان سروری ساخته و نگهداری می‌شوند که به آن تعلق دارند. پس از جفت‌سازی، سرویس‌های تونل همچنان خاموش می‌مانند تا اپراتور صریحاً آن‌ها را روشن کند.

## نصب یک‌خطی

ابتدا یک VPS آزمایشی Ubuntu/Debian برای Gateway آماده کن. دستور زیر را فقط روی Gateway اجرا کن. به‌جای `YOUR_PUBLIC_IP_OR_DNS` آدرس IP عمومی یا نام DNS واقعی Gateway را قرار بده؛ مقدار نمونه را عیناً وارد نکن.

### روی Gateway

```sh
curl -fsSL https://raw.githubusercontent.com/hatinati2/PQTunnel-2/COMMIT_SHA/scripts/pqtunnel-control-install.sh | sudo bash -s -- --ref COMMIT_SHA --role gateway --panel-host YOUR_PUBLIC_IP_OR_DNS --panel-port 6100
```

- `COMMIT_SHA` باید SHA چهل‌کاراکتری commit بازبینی‌شده باشد.
- فقط TCP/6100 (یا پورت انتخابی) را برای پنل باز کن.
- TCP/80 و Certbot برای پنل HTTP لازم نیستند.
- پنل از URL خصوصی‌ای که نصاب چاپ می‌کند قابل دسترسی است. URL و توکن ورود را محرمانه نگه دار.
- نصاب سرویس Manager و endpoint را نصب می‌کند؛ سرویس تونل را شروع نمی‌کند.

### روی Dialer

از پنل Gateway گزینهٔ ساخت دعوت/دستور نصب Dialer را انتخاب کن. دستور تولیدشده را فقط روی VPS دوم اجرا کن. Agent پس از enrollment به‌صورت سرویس فعال می‌شود و باید در داشبورد به حالت متصل برسد.

## هشدار امنیتی مهم دربارهٔ HTTP

HTTP رمزگذاری انتقال ندارد. مسیر ۲۵۶ بیتی و توکن ورود جای TLS را نمی‌گیرند. هر کسی که بتواند ترافیک شبکه را شنود یا دست‌کاری کند ممکن است توکن ورود، کوکی نشست یا دعوت اولیهٔ Dialer را مشاهده یا تغییر دهد.

برای همین این build را فقط در محیط آزمایش استفاده کن:
- پورت پنل را در فایروال سیستم و فایروال ارائه‌دهنده فقط به IP مدیریتی خودت محدود کن.
- از Wi-Fi عمومی یا شبکهٔ غیرقابل‌اعتماد وارد پنل نشو.
- URL محرمانه و توکن را در اسکرین‌شات، تیکت یا لاگ عمومی قرار نده.
- روی سرور عملیاتی یا برای مدیریت اطلاعات حساس از این حالت استفاده نکن.

**این تغییر فقط مربوط به پنل و کانال کنترل آزمایشی است.** خود تونل داده همچنان از TLS 1.3 و احراز هویت گواهی استفاده می‌کند؛ این دو مسیر را نباید با هم اشتباه گرفت.

## چه چیزی هنوز مدیریت نمی‌شود؟

این داشبورد چرخهٔ عمر سرویس، تنظیمات پشتیبانی‌شده، پروفایل‌های PKI و لاگ‌ها را مدیریت می‌کند؛ اما هنوز مدیریت کامل default route، policy routing، NAT، IP forwarding، firewall یا kill-switch ممیزی‌شده را ارائه نمی‌دهد. جفت‌سازی موفق به‌تنهایی به معنی آماده بودن مسیر دلخواه ترافیک نیست.

## وضعیت اعتبارسنجی

- CI، بررسی امنیتی خودکار و Fuzz روی commit مشخص‌شده باید در GitHub Actions سبز باشند.
- تست‌های namespace محلی جایگزین تست دو VPS واقعی، فایروال ارائه‌دهنده، قطع و وصل واقعی اینترنت یا ممیزی مستقل نیستند.
- قبل از هرگونه استفادهٔ عملیاتی، تست دو میزبان، بررسی مستقل امنیت و runbook بازیابی لازم است.
