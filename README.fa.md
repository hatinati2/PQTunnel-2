# PQTunnel 2

**نسخه: 0.4.0-pqalpha.1** · **وضعیت: شاخهٔ توسعهٔ آزمایشی، غیرآماده برای استفادهٔ عملیاتی.**

PQTunnel 2 یک شاخهٔ مستقل و آزمایشی از پروژهٔ تونل لایهٔ ۳ است که از TLS 1.3، احراز هویت دوطرفه و الگوریتم‌های پساکوانتومی استفاده می‌کند. این مخزن از پروژهٔ قبلی PQTunnel جدا نگه داشته شده است.

> **وضعیت: آزمایشی و غیرآماده برای استفادهٔ عملیاتی.** پروژه ممیزی امنیتی مستقل نشده است. برای فعالیت حساس یا روی سرور عملیاتی از آن استفاده نکن.

## طراحی رمزنگاری

### احراز هویت

ابزار `pqtunnel-pki` برای CA، سرور، کلاینت و Peer کلیدهای **ML-DSA-65** مطابق FIPS 204 تولید می‌کند. امضای تمام گواهی‌ها نیز ML-DSA-65 است. هر دو سمت TLS زنجیرهٔ گواهی ارائه‌شده و زنجیرهٔ تأییدشده را بررسی می‌کنند؛ تمام گواهی‌ها باید کلید عمومی و امضای ML-DSA-65 داشته باشند. گواهی‌های کلاسیک، از جمله Ed25519، رد می‌شوند.

### حالت‌های تبادل کلید

هر دو سمت تونل باید از یک حالت یکسان استفاده کنند:

| حالت | تبادل کلید TLS 1.3 | احراز هویت | وضعیت |
|---|---|---|---|
| `hybrid` (پیش‌فرض) | X25519 + ML-KEM-768 | ML-DSA-65 | حالت پیشنهادی برای تست سازگاری |
| `pure-pq` | فقط ML-KEM-1024 | ML-DSA-65 | آزمایشی، بدون fallback کلاسیک |

حالت پیش‌فرض Hybrid دارای احراز هویت پساکوانتومی و تبادل کلید ترکیبی است؛ اما **تبادل کلید کاملاً پساکوانتومی نیست** چون X25519 کلاسیک هم دارد. حالت `pure-pq` مؤلفهٔ کلاسیک تبادل کلید را حذف می‌کند؛ ولی تا زمانی که سازگاری و پذیرش عملی آن در محیط واقعی بررسی نشده، فقط برای آزمایش است.

حالت را در هر دو برنامه با `--tls-key-exchange` یا متغیر `PQTUNNEL_TLS_KEX` تعیین کن. مقدار ناشناخته رد می‌شود. هر پیکربندی فقط یک گروه تبادل کلید را مجاز می‌داند و fallback به الگوریتم کلاسیک وجود ندارد.

### پیش‌نیازها

- حداقل Go **1.27** لازم است. Go 1.27 بستهٔ استاندارد `crypto/mldsa` و پشتیبانی ML-DSA در X.509 و TLS 1.3 را اضافه کرده است.
- هدف MVP آزمایشی: Linux، اوبونتو 24.04/26.04 و معماری amd64/arm64.
- فقط TLS 1.3 فعال است.
- فرمان `verify` همین ابزار، زنجیرهٔ گواهی، SAN/CN، EKU، تطابق کلید، الگوریتم ML-DSA-65 و مجوز فایل کلید خصوصی را با پیاده‌سازی X.509/TLS در Go بررسی می‌کند و به نسخهٔ OpenSSL سیستم وابسته نیست؛ بنابراین با OpenSSL 3.0 پیش‌فرض اوبونتو 24.04 نیز سازگار است. کلید خصوصی CA باید آفلاین و محرمانه بماند.

## ساخت و تست

از ریشهٔ مخزن اجرا کن:

```sh
go test -race ./...
go vet ./...
go build ./cmd/pqtunneld ./cmd/pqtunnel-client ./cmd/pqtunnel-pki ./cmd/pqtunnel-manager ./cmd/pqtunnel-proxy
```

CI تست‌های واحد، race، تحلیل ایستا، cross-build و آزمایش‌های network namespace ایزوله را اجرا می‌کند. تست‌های network namespace در آزمایشگاه‌های موقت محلی اجرا می‌شوند؛ به VPS واقعی متصل نمی‌شوند و فایروال ارائه‌دهنده یا بازیابی ارتباط بین دو سرور واقعی را تأیید نمی‌کنند.

## ساخت PKI آزمایشی جدید

برای آزمایش از مسیر موقت و مقادیر ساختگی مخصوص مستندسازی استفاده کن:

```sh
tmp="$(mktemp -d)"
chmod 700 "$tmp"
go run ./cmd/pqtunnel-pki init --out "$tmp/pki" --server-name vpn.example.test
go run ./cmd/pqtunnel-pki issue-client --out "$tmp/pki" --ip 192.0.2.10
go run ./cmd/pqtunnel-pki issue-peer --out "$tmp/pki" --name peer-fixture
go run ./cmd/pqtunnel-pki verify --purpose server --cert "$tmp/pki/server.crt" --key "$tmp/pki/server.key" --ca "$tmp/pki/ca.crt" --server-name vpn.example.test
```

آدرس کلاینت نمونه از محدودهٔ رزروشدهٔ مستندسازی است و endpoint واقعی نیست. مقادیر محیط واقعی را فقط هنگام اجرا و از طریق فایل پیکربندی محافظت‌شده وارد کن؛ IP، دامنه، پورت، توکن، رمز، گواهی یا کلید خصوصی‌ای که مدیر سیستم ارائه می‌کند نباید در کد، تست، fixture، CI، اسکرین‌شات یا لاگ ثبت شود.

برای هر نصب، CA جدید بساز و گواهی‌های جدید سرور/کلاینت/Peer صادر کن. گواهی‌های Ed25519 نسخهٔ قبلی PQTunnel عمداً ناسازگارند و نباید دوباره استفاده شوند. کلید خصوصی CA را به هیچ‌یک از دو سمت تونل منتقل نکن.

## وضعیت پلتفرم‌ها

- **Linux:** پلتفرم هدف برای MVP آزمایشی.
- **Windows:** پشتیبانی نمی‌شود؛ cross-build به‌تنهایی به معنی تست پلتفرم نیست.
- **Android:** فقط scaffold؛ تنظیم DNS، واردکردن گواهی، چرخهٔ عمر و تست روی دستگاه واقعی کامل نشده‌اند.

## محدودیت‌های مهم

- ممیزی امنیتی مستقل و fuzzing کامل انجام نشده است.
- سامانهٔ ابطال آنلاین گواهی یا enrollment خودکار امن وجود ندارد.
- اسکریپت‌های route و firewall لینوکس نمونهٔ اولیه‌اند و kill-switch ممیزی‌شده و ماندگار نیستند.
- انتقال فعلی روی TCP است و ممکن است مشکل TCP-over-TCP و head-of-line blocking داشته باشد.
- حالت `pure-pq` آزمایشی است و تا زمان اعتبارسنجی جداگانه نباید سازگار با همهٔ پیاده‌سازی‌ها یا آمادهٔ تولید معرفی شود.
- هیچ ساختار رمزنگاری‌ای غیرقابل‌شکستن یا بدون ریسک تضمین نمی‌شود.
