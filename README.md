# PQTunnel 2

PQTunnel 2 is an experimental Linux-first Layer-3 tunnel with mutual TLS 1.3 authentication and post-quantum cryptographic algorithms. It is maintained in a separate repository from the original PQTunnel project.

> **Status: experimental / not production-ready.** This repository has not undergone an independent security audit. Do not use it to protect sensitive activity or deploy it on production infrastructure.

## Cryptographic design

### Authentication

Every CA, server, client, and peer key generated by `pqtunnel-pki` uses **ML-DSA-65** (FIPS 204). Certificates are signed with ML-DSA-65. Both TLS endpoints enforce the peer's presented and verified certificate chain: all certificates must contain ML-DSA-65 public keys and ML-DSA-65 signatures. Classical certificate chains, including Ed25519, are rejected.

### Key exchange modes

Both endpoints must use the same mode:

| Mode | TLS 1.3 key exchange | Authentication | Status |
|---|---|---|---|
| `hybrid` (default) | X25519 + ML-KEM-768 | ML-DSA-65 | Recommended for interoperability testing |
| `pure-pq` | ML-KEM-1024 only | ML-DSA-65 | Experimental; no classical key-exchange fallback |

The default hybrid mode has post-quantum authentication and a hybrid key exchange, but it is **not a pure post-quantum key exchange** because it still includes X25519. The `pure-pq` mode removes that classical key-exchange component. It remains opt-in until interoperability and real deployment acceptance have been demonstrated.

Select the mode on both daemon and client with `--tls-key-exchange` or `PQTUNNEL_TLS_KEX`. Unknown values are rejected. Each configuration advertises exactly one key-exchange group; there is no fallback to a classical group.

### Runtime requirements

- Go **1.27 or newer** is required. Go 1.27 adds the standard-library `crypto/mldsa` package and ML-DSA support in X.509 and TLS 1.3.
- Linux MVP target: Ubuntu 24.04/26.04, amd64 and arm64.
- TLS 1.3 is the only enabled TLS version.
- The standalone PKI tool generates ML-DSA-65 keys and X.509 certificates. Keep the CA private key offline.

## Build and test

From the repository root:

```sh
go test -race ./...
go vet ./...
go build ./cmd/pqtunneld ./cmd/pqtunnel-client ./cmd/pqtunnel-pki ./cmd/pqtunnel-manager ./cmd/pqtunnel-proxy
```

CI runs unit, race, static-analysis, cross-build, and isolated network-namespace tests. Network-namespace tests are disposable local labs. They do not connect to operator VPSs or validate provider firewalls, arbitrary host firewall policies, or real two-host recovery.

## Create a fresh test PKI

Use a temporary directory and synthetic documentation-only identity values when testing:

```sh
tmp="$(mktemp -d)"
chmod 700 "$tmp"
go run ./cmd/pqtunnel-pki init --out "$tmp/pki" --server-name vpn.example.test
go run ./cmd/pqtunnel-pki issue-client --out "$tmp/pki" --ip 192.0.2.10
go run ./cmd/pqtunnel-pki issue-peer --out "$tmp/pki" --name peer-fixture
```

The example client address is from the documentation-only TEST-NET range and is not an endpoint to connect to. Use your own deployment values only at runtime, through protected configuration; never copy operator addresses, credentials, tokens, certificates, or private keys into source files, tests, fixtures, CI, screenshots, or logs.

For every deployment, create a new CA and issue new server/client/peer certificates. Existing Ed25519 certificates from the original PQTunnel repository are intentionally incompatible and must not be reused. Do not copy the CA private key to either tunnel endpoint.

## Platform status

- **Linux:** target platform for the experimental MVP.
- **Windows:** unsupported; a cross-build is not platform validation.
- **Android:** scaffold only; DNS, certificate onboarding, lifecycle management, and physical-device testing are incomplete.

## Important limitations

- No independent security audit or full fuzzing campaign has been completed.
- No online certificate revocation service or safe automated enrollment system is provided.
- The Linux route and firewall helpers are prototypes, not a persistent audited kill-switch.
- The transport currently uses TCP and can experience TCP-over-TCP head-of-line blocking.
- `pure-pq` is experimental and must not be represented as interoperable or production-ready until separately validated.
- This project does not claim that any cryptographic construction is unbreakable or that the entire system is risk-free.

See [SECURITY.md](SECURITY.md), [the protocol description](docs/PROTOCOL.md), and the [Linux MVP release gates](docs/LINUX-MVP-RELEASE-GATE.md).
